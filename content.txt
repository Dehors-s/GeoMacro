## 1️⃣ 推荐的端到端技术生命周期

```
┌─────────────────────────────────────────────────────────────┐
│ 历史采集 → 规范化 → 变量识别 → 模板生成 → 验证 → 输出
└─────────────────────────────────────────────────────────────┘
```

| 阶段 | 职责 | 输入 | 输出 |
|-----|------|------|------|
| **采集** | 从ArcGIS Pro历史获取原始事件 | 项目.aprx / 日志 | 原始事件列表 |
| **规范化** | 统一事件格式、提取工具名/参数 | 原始事件 | 标准化事件对象 |
| **变量识别** | 识别可变参数（路径、数值、字符串）并提取模式 | 标准化事件 | 参数映射表+变量分类 |
| **模板生成** | 根据工具类型和参数特征生成对应脚本模板 | 参数映射表 | Python/Batch脚本模板 |
| **验证** | 语法检查、参数合法性、环境兼容性 | 脚本模板 | 验证报告 |
| **输出** | 生成可执行脚本或add-in配置 | 验证报告 | .py/.bat 脚本 |

**假设/需验证项**：
- ArcGIS Pro 是否暴露 geoprocessing 历史的完整API（`arcpy.gp` 或项目对象）
- 是否支持流式读取大规模历史（分页/增量机制）

## 2️⃣ 监听/抓取策略对比

### **策略1：主动轮询历史（推荐MVP）**
```
优点：
  ✅ 实现最简单，无依赖复杂事件系统
  ✅ 支持离线回溯（可从历史查找任意时间段操作）
  ✅ 兼容性最好（任何ArcGIS Pro版本都支持）

缺点：
  ❌ 需要定期轮询（可能有延迟）
  ❌ 可能重复处理相同事件（需去重）
  ❌ 历史可能被清理（取决于ArcGIS Pro保留策略）

实现难度: ⭐⭐
```

### **策略2：从项目历史XML读取**
```
优点：
  ✅ 原始数据完整（可能包含中间步骤）
  ✅ 一次性读取，无重复处理

缺点：
  ❌ 需要解析项目文件格式（可能随版本变化）
  ❌ 涉及文件I/O锁定问题（项目打开时）
  ❌ 字段映射复杂（需逆向工程）

实现难度: ⭐⭐⭐
```

### **策略3：从结果对象/日志抓取**
```
优点：
  ✅ 可获取执行时间戳、耗时、错误等元数据

缺点：
  ❌ 信息不完整（可能丢失某些参数细节）
  ❌ 格式不统一（不同工具差异大）

实现难度: ⭐⭐⭐⭐
```

### **策略4：事件/钩子监听（如存在）**
```
优点：
  ✅ 实时捕获，无延迟

缺点：
  ❌ ArcGIS Pro Python API 未确认是否暴露此API
  ❌ 可能需要C++扩展或低级挂钩

实现难度: ⭐⭐⭐⭐⭐ （非常不确定可行性）
```

### **🎯 MVP推荐**
**结合策略1 + 策略3**：
- 主轮询从项目历史读取 Geoprocessing 操作列表
- 补充从最近的"结果"面板获取元数据（耗时、参数完整性）
- 预期延迟：< 5 秒，可接受范围

### **详细模块设计**

| 模块 | 职责 | 关键输入 | 关键输出 | 依赖 |
|-----|------|---------|---------|------|
| **HistoryCollector** | 从项目/日志读取GP历史 | Project对象/日志路径 | List[GeoprocessEvent] | arcpy |
| **EventNormalizer** | 统一事件格式、参数提取 | List[GeoprocessEvent] | List[StandardEvent] | - |
| **ParameterExtractor** | 提取工具参数、分类（路径/数值/字符串/要素类等） | StandardEvent | ParameterMap | - |
| **VariableIdentifier** | 识别可变部分、生成变量声明 | ParameterMap | VariableSet + ConstantSet | - |
| **TemplateMapper** | 根据工具类型映射到脚本模板 | VariableSet + ToolName | ScriptTemplate | ToolRegistry |
| **CodeBuilder** | 填充模板，生成最终脚本 | ScriptTemplate + VariableValues | FinalScript | - |
| **SyntaxValidator** | 检查Python/Batch语法 | FinalScript | ValidationReport | - |
| **EnvironmentValidator** | 检查路径有效性、环境变量 | FinalScript | EnvironmentReport | - |
| **DryRunExecutor** | 可选的试运行（仅验证，不写入） | FinalScript | ExecutionLog | arcpy |
| **UIPanel** | add-in面板（展示历史、生成、预览、执行） | - | 用户操作信号 | 所有模块 |

## 4️⃣ 需要重点处理的 Edge Cases（10+，按严重度分组）

### **🔴 高严重度（影响核心功能）**

1. **多工具顺序执行时的依赖链**
   - 问题：工具B的输入是工具A的输出，变量识别需要追踪依赖关系
   - 例如：`FeatureClassToShapefile(input_fc, output_shp) → Dissolve(output_shp)`
   - 处理方案：构建有向无环图(DAG)，验证拓扑顺序

2. **参数中包含中文路径/字符**
   - 问题：编码错误导致脚本失效（特别是在Windows Batch中）
   - 处理方案：检测并转换为UNC路径或环境变量引用

3. **临时中间数据的生命周期不清**
   - 问题：脚本重复执行时，临时数据是否需要清理？是否应该复用？
   - 处理方案：追踪数据源，区分"输入数据（稳定）"vs"中间数据（临时）"

4. **地理坐标系/投影系统不匹配**
   - 问题：如果历史中工具使用了特定投影，脚本生成后在不同数据集上可能失效
   - 处理方案：检测并记录空间参考系，生成检查代码

5. **参数值中包含特殊字符或SQL表达式**
   - 问题：如 `"NAME = 'user's input'"`，转义错误导致执行失败
   - 处理方案：参数值分类处理，对SQL表达式/路径/字符串分别转义

### **🟠 中严重度（影响稳定性）**

6. **历史记录中缺失参数信息**
   - 问题：某些工具参数未在历史中记录，脚本生成时参数不完整
   - 处理方案：识别缺失参数，提示用户补充或使用默认值；标记为"高风险参数"

7. **多个用户同时运行GeoMacro时的并发冲突**
   - 问题：两个用户同时生成脚本，可能读取到不一致的历史状态
   - 处理方案：实现文件锁机制或时间戳隔离

8. **Batch脚本中的路径长度超过260字符（Windows限制）**
   - 问题：GIS数据路径可能很深，超过限制导致脚本失效
   - 处理方案：自动使用 `SET SHORT_PATH` 或 UNC 前缀

9. **工具参数顺序不匹配（位置参数 vs 命名参数）**
   - 问题：arcpy工具既支持位置参数也支持命名参数，历史中可能是混合形式
   - 处理方案：规范化为命名参数形式（更稳定）

10. **工具版本不兼容（跨ArcGIS Pro版本）**
    - 问题：历史中记录的工具在旧版本中不存在或参数不同
    - 处理方案：记录工具执行时的ArcGIS Pro版本号，脚本生成时进行版本检查

### **🟡 低严重度（需要改进但不阻塞MVP）**

11. **光栅/矢量混合的复杂参数类型**
    - 问题：某些工具参数可以接受光栅或矢量数据，类型推断困难
    - 处理方案：保守策略，标记为"动态参数"，生成提示用户手动验证

12. **循环引用检测（如果允许工具链编辑）**
    - 问题：用户可能创建 A→B→A 这样的循环
    - 处理方案：DAG拓扑检查

### **✅ IN SCOPE（必须实现）**

#### **核心功能**
1. **历史采集**：轮询从当前项目读取最近 N 条 Geoprocessing 操作
   - 支持的工具类型：Dissolve, Buffer, Merge, Clip, FeatureClassToShapefile（基础5-10个）
   - 参数提取：基本字段类型（路径、数值、字符串）

2. **脚本生成**：从选中的操作生成 Python 脚本（Batch 作为 Phase 2）
   - 支持单工具生成
   - 支持多工具链（简单的线性依赖）

3. **参数识别**：基础变量提取（相同值→常量，不同值→变量）

4. **验证**：
   - 语法检查（Python ast.parse）
   - 基础路径检查（文件存在性）

5. **MVP UI 面板**：
   - 历史列表展示 + 多选
   - 脚本预览
   - [生成脚本] [保存] 两个主按钮

#### **技术栈**
- Python + arcpy（基于 ArcGIS Pro 的标准库）
- 简单的 UI（WPF XAML 或 PyQt5，如果add-in框架允许）
- 单机本地（无云、无数据库）

---

### **❌ OUT OF SCOPE（Phase 2/3）**

1. ❌ **Batch 脚本生成**（Python 版本稳定后再做）
2. ❌ **复杂参数类型处理**：光栅、矢量混合、SQL表达式、高级空间参考系
3. ❌ **多工具非线性依赖**（如分支、循环）
4. ❌ **工具链编辑UI**（只支持读取历史，不支持用户创建新工具链）
5. ❌ **实时执行/Dry-run**（只生成脚本，不执行）
6. ❌ **跨项目/工作空间支持**
7. ❌ **版本兼容性**（假设单一 ArcGIS Pro 版本）
8. ❌ **高级错误恢复**（如果脚本执行失败，Phase 2 再做自动回滚）
9. ❌ **性能优化**（假设历史 < 100条）
10. ❌ **国际化**（中文UI可接受）

## 📊 技术决策矩阵

| 决策点 | 选项 | MVP决策 | 理由 |
|-------|------|--------|------|
| 监听策略 | 轮询 vs 事件 vs XML解析 | **轮询** | 最稳定、实现快 |
| 脚本语言 | Python vs Batch | **Python优先** | 语法简单、易验证 |
| 参数识别 | 模式匹配 vs 规则引擎 | **简单规则** | 学生团队易理解 |
| UI框架 | 原生WPF vs PyQt vs Web | **原生add-in UI** | 与ArcGIS Pro集成最紧 |
| 存储 | 本地文件 vs 数据库 | **本地JSON** | 简化部署 |
